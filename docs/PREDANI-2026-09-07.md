# Ollama logging proxy — stav projektu k 7. 9. 2026

Předávací dokument pro nové vlákno. Obsahuje architekturu, historii nasazení,
vyřešené i otevřené problémy a diagnostické příkazy.

---

## 1. Co to je

Transparentní reverse proxy (FastAPI) mezi klientem a Ollama API. Streamuje
odpovědi beze změny, cestou sbírá metriky a loguje do SQLite. Má vlastní webové
GUI pro prohlížení historie.

**Motivace:** Open WebUI nenabízí přehled spotřeby tokenů. Proxy zachytává
nativní metadata Ollamy (`prompt_eval_count`, `eval_count`, `total_duration`,
`eval_duration`) a počítá tokens/sec.

**Nová funkce (zatím nenasazená):** ke každému dotazu se ukládá i stav serveru
v okamžiku příchodu requestu — umístění modelu (GPU/CPU/split), procento modelu
ve VRAM, load hostitele, volná RAM a počet souběžných dotazů. Účelem je
diagnostika občasných výpadků odpovědí.

## 3. Architektura běhu

```
klient ──► Caddy :11435 ──► ollama-proxy :11435 ──► open-webui:11434 (Ollama)
                │                    │
                │                    └─► SQLite /data/ollama_log.db
                └─ Caddy :11436 (basic auth) ──► /ui
```

- **Port 11435** — holé Ollama API, bez autentizace, cesta `/ui` blokovaná (403)
- **Port 11436** — GUI za bcrypt basic auth
- Docker síť **`ollamaNet`**; proxy se musí nasadit **první**, jinak ji Open
  WebUI nemá jak referencovat
- Volume **`ollamaproxy_data`** připojený na `/data`
- Open WebUI míří na proxy přes Admin → Settings → **Connections**
  (`http://ollama-proxy:11435`)

### Konfigurace přes ENV

| Proměnná | Hodnota | Význam |
|---|---|---|
| `OLLAMA_UPSTREAM` | `http://open-webui:11434` | cíl proxy (ověřeno) |
| `OLLAMA_LOG_DB` | `/data/ollama_log.db` | cesta k SQLite |
| `OLLAMA_LOG_BODIES` | `1` | ukládat request JSON a text odpovědi |
| `PROXY_PORT` | `11435` | port uvicornu |

## 5. Schéma databáze

Tabulka `requests`:

```
id, ts, endpoint, model, status,
prompt_tokens, completion_tokens,
total_duration_ms, eval_duration_ms, tokens_per_sec, wall_time_ms,
request_json, response_text,
-- přidané za běhu přes ALTER TABLE:
placement, vram_pct, loaded_model, load1, load5, mem_avail_pct, concurrent
```

`placement` nabývá: `gpu` (≥99 % modelu ve VRAM), `split`, `cpu` (<1 %),
`none` (model není načtený), `unknown` (`/api/ps` nedostupné).

**POZOR:** schéma nové verze je rekonstruované, nebylo ověřeno proti reálné
existující DB. Před nasazením zkontrolovat:

```bash
docker run --rm -v ollamaproxy_data:/x python:3.12-slim python3 -c \
  "import sqlite3;print(sqlite3.connect('/x/ollama_log.db').execute(\"select sql from sqlite_master where type='table'\").fetchall())"
```

Pokud se názvy sloupců liší, upravit konstantu `SCHEMA` v Pythonu.

## 6. Vyřešené problémy (nešlapat do nich znovu)

### 6.1 TrueNAS template parser rozbíjí Python v YAML
`build: .` v „Install via YAML" nefunguje (chybí build context) → nutný
`dockerfile_inline`. Ale Python vložený heredocem selhal: TrueNAS renderovací
pipeline bere bare `{slovo}` (konkrétně `{q}` z query parametru) jako template
control keyword.

**Řešení:** celý skript zabase64ovat, v Dockerfile dekódovat:
`RUN echo '<base64>' | base64 -d > /app/ollama_logging_proxy.py`.
V YAML pak nejsou žádné složené závorky (kromě Caddyfile bloku, ten je OK).

### 6.2 Anonymní volume → ztráta dat při každém redeployi
Původní YAML měl:
```yaml
volumes:
  - target: /data
    type: volume
    volume: {}
```
To je **anonymní** volume; pojmenovaný `ollamaproxy_data` v sekci `volumes:`
se nikam nepřipojoval. Po recreate kontejneru vzniklo nové → prázdná DB.

**Řešení:**
```yaml
volumes:
  - type: volume
    source: ollama-proxy-data
    target: /data
```

Historická data pravděpodobně zůstala v osiřelých anonymních volumes.
Skenování bylo rozjeté, ale nedoběhlo — nalezen minimálně
`3c82e146824c813fc11a4ffb80a4562cb9fd3a152e811aa4c7799e4ed43daa04` plus
několik dalších (výstup se ztratil při reloadu okna). **Neprovádět
`docker volume prune`, dokud se to nedořeší.**

### 6.3 Basic auth přes `{env.*}` nefunguje
Caddyfile měl:
```
basicauth {
  {env.GUI_USER} {env.GUI_PASS_HASH}
}
```
Caddy parsuje bcrypt hash při načítání configu, kdy placeholder ještě není
rozvinutý. Directive se načte bez chyby (proxy běží), ale porovnání hesla
selže vždy.

**Řešení:** hash a uživatel napevno v Caddyfile, generuje `make_yaml.sh`.
Zároveň v Caddy 2.8+ se directive jmenuje `basic_auth`, `basicauth` je
deprecated alias.

Druhá past: v compose se `$` interpoluje, hash musí mít každý `$` **zdvojený**
(`$$2a$$14$$...`). `make_yaml.sh` to dělá automaticky přes `sed`.

### 6.4 Shell drobnosti
- `sudo kill %1` nefunguje — `%1` je konstrukt shellu, ne argument programu
- Suspendovaný proces (`suspended (tty output)`) ignoruje `SIGTERM`; nutné
  `kill -CONT` a pak `kill`, nebo rovnou `kill -9`
- `nohup sudo ...` na pozadí se zasekne na dotazu na heslo → `sudo -v` předem
  a pak `sudo -n`, nebo pracovat v `sudo -i`
- V `python:3.12-slim` není `curl`; testovat přes `python3 -c "import urllib.request; ..."`

## 7. Otevřený problém — Ollama běží na CPU

**Příznak:** Open WebUI kontejner drží 10,65 GiB RAM (odpovídá velikosti
gemma4:12b), CPU 35 %, v chatu odpovědi nepřicházejí. Model je v RAM, ne ve
VRAM. ComfyUI je odpojené, takže GPU konflikt to není.

**Hypotéza:** po updatu TrueNASu / appky / driveru se ztratilo přiřazení GPU,
nebo spadl nvidia driver.

Na CPU dá gemma4:12b řádově 1–3 tok/s → odpověď na 500 tokenů trvá 3–8 minut,
Open WebUI mezitím spadne do timeoutu a uživatel vidí prázdno.

### Diagnostika (nebyla dosud provedena)

```bash
sudo -i
docker ps --format '{{.Names}}\t{{.Image}}' | grep -i -E 'open-webui|ollama'

nvidia-smi                                          # vidí kartu hostitel?
docker exec ix-open-webui-open-webui-1 nvidia-smi   # vidí ji kontejner?
docker inspect ix-open-webui-open-webui-1 --format '{{json .HostConfig.DeviceRequests}}'
docker exec ix-open-webui-open-webui-1 sh -c 'curl -s localhost:11434/api/ps'
docker logs --tail 200 ix-open-webui-open-webui-1 2>&1 \
  | grep -iE 'cuda|gpu|offload|layers|no compatible|libcuda'
```

Rozlišení:
- `DeviceRequests` je `null` → GPU není appce přiřazená → Apps → open-webui →
  Edit → Resources Configuration → GPU Configuration → zaškrtnout RTX 3060
- hostitelský `nvidia-smi` selže → spadl driver → `modprobe nvidia`, případně
  Apps → Configuration → Install NVIDIA Drivers, nebo reboot
- v logu `no compatible GPUs were discovered` / `libcuda.so not found` → chybí
  nvidia container runtime u té appky
- `offloaded 0/49 layers to GPU` → potvrzený čistý CPU běh

### Ověření po opravě

```bash
docker exec ix-open-webui-open-webui-1 sh -c \
  'curl -s -X POST localhost:11434/api/generate -d "{\"model\":\"gemma4:12b\",\"prompt\":\"ahoj\",\"stream\":false}"' \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(round(d["eval_count"]/(d["eval_duration"]/1e9),1),"tok/s")'
```

Na RTX 3060 očekávat **25–45 tok/s**. Pod 5 tok/s = pořád CPU.

### Doporučené nastavení po opravě

Do env Open WebUI přidat `OLLAMA_KEEP_ALIVE=-1` — drží model ve VRAM natrvalo.
Default je 5 minut, po kterých se model uvolní a další dotaz čeká 30–90 s na
reload; to uživatel vnímá jako „neodpovídá".

## 8. Čtyři hypotézy pro „občas neodpovídá"

Nová telemetrie je má od sebe odlišit:

| # | Příčina | Signatura v logu |
|---|---|---|
| 1 | Unload po `keep_alive` | předchozí záznam `placement=none`, vysoký `wall_time_ms` při normálním `tokens_per_sec` |
| 2 | Fronta při souběhu (`OLLAMA_NUM_PARALLEL=1`) | `concurrent > 1`, `wall_time_ms` >> `total_duration_ms` |
| 3 | Tichý propad na CPU | `placement=cpu` nebo `split`, `vram_pct` pod 100 |
| 4 | Timeout před proxy (CF Tunnel 100 s, NPM `proxy_read_timeout` 60 s) | záznam **chybí úplně**, nebo `status=599` |

Rozlišovací dotaz po pár dnech provozu:

```sql
SELECT placement, count(*) n,
       round(avg(tokens_per_sec),1) tps,
       round(avg(wall_time_ms - coalesce(total_duration_ms,0))) load_ms
FROM requests GROUP BY placement;
```

`load_ms` = čas mimo generaci (čekání na reload modelu nebo na frontu).
